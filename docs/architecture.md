## Data flow: intake

```
User submits intake form
        |
        v
POST /api/intake
        |
        v
1. Validate input, sanitize deployment name (letters/digits/hyphens)
2. Foundry: create project (if requested)
        |  ARM PUT /projects/<name>  (API 2025-04-01-preview, identity: SystemAssigned)
3. Foundry: create model deployment
        |  ARM PUT /deployments/<name>
        |  raiPolicyName = Microsoft.DefaultV2 (or skip for embeddings)
4. APIM: create API + operations
        |  displayName, path, protocols
5. APIM: apply policy XML with placeholders substituted
        |  ({DEPLOYMENT_NAME}, {TPM_LIMIT}, {APP_NAME}, ...)
6. APIM: create subscription for this API
        |  primaryKey generated by APIM
7. Key Vault: put secret with subscription's primaryKey
        |  tags: app_name, app_owner, ...
8. DB: insert DeploymentRecord (single source of truth for "governed state")
9. Audit log: intake success event
        |
        v
Return { deployment_name, apim_endpoint, kv_secret_uri, ... }
```

If any stage fails, the response includes the stage tag (`foundry`, `apim`, `keyvault`, ...) and the raw error message. Partial state is left in place for debugging; the delete cascade will clean it up on retry.

## Data flow: budget enforcement

```
Every 60s (background worker):
        |
        v
For each active DeploymentRecord:
        |
        +-> KQL against Log Analytics:
        |     AzureDiagnostics
        |     | where ResourceId endswith apim_service
        |     | where DeploymentName_s == deployment_name
        |     | summarize prompt=sum(PromptTokens_d), completion=sum(CompletionTokens_d)
        |
        +-> Retail Prices lookup for (model_name, sku_hint)
        |     hardcoded table first (known models: gpt-4o family, gpt-3.5, embeddings)
        |     Retail API fallback: serviceName eq 'Foundry Models', region fallback list
        |     exclude batch / cached / FT SKUs; prefer lowest tie-break
        |     24h cache
        |
        +-> cost_usd = prompt/1M * input_price + completion/1M * output_price
        |   burn_pct = 100 * cost_usd / monthly_budget_usd
        |
        +-> If burn_pct >= threshold_pct and state == "active":
              1. APIM: PATCH subscription state = suspended
              2. APIM: rewrite policy so <check-header> gate matches deployment name
                 and returns 429 with retry-after
              3. APIM: append deployment_name to "watchtower-suspended-deployments" named value
              4. DB: state = "suspended"
              5. Audit log: auto-suspend event
```

The three-layer suspend is intentional. Any one of them would work in isolation, but layering means an accidental APIM policy re-push (unrelated deploy, config drift undo, etc.) will not silently un-suspend an over-budget endpoint.

## Data flow: config drift

```
User opens deployment drawer
        |
        v
GET /api/deployments/{name}/config-drift
        |
        +-> Query Azure Activity Log (last 30 days) for:
        |     - Microsoft.CognitiveServices/accounts/deployments/write on this deployment
        |     - Microsoft.ApiManagement/service/apis/write on the APIM API
        |     - Microsoft.KeyVault/vaults/secrets/write on the KV secret
        |
        +-> Compare "governed state" (DB DeploymentRecord fields) vs
            current state fetched from ARM
        |
        +-> Return diff array:
            [{ field: "tpm_limit", governed: 100000, actual: 500000, changed_by: "...", changed_at: "..." }]
```

Drift does not auto-heal. The UI surfaces the diff and the operator decides: re-apply governed state (single button) or update the DB to match the manual change (accepting new baseline).

## Data model (DB)

Two primary tables:

**DeploymentRecord** - the "governed state" for each APIM-published endpoint. Fields include:
- Identity: `deployment_name`, `project_name`, `model_name`, `model_version`, `sku_name`, `capacity`
- Ownership: `app_name`, `app_owner`, `app_team`, `business_unit`, `environment`, `cost_center`, `use_case_description`
- Enforcement: `tpm_limit`, `throttling_rpm`, `monthly_budget_usd`, `threshold_pct`
- Azure references: `apim_api_id`, `apim_subscription_id`, `kv_secret_uri`
- State: `state` ("active" / "suspended" / "deleted"), `created_at`, `updated_at`

**AuditLog** - append-only event stream. `actor`, `action`, `target_type`, `target_id`, `before`, `after`, `at`. Used for intake / update / delete / auto-suspend / policy-reapply events. Never edited.

## Authentication

- **User -> Watchtower**: none in this release. If deployed publicly, put App Service Authentication (Easy Auth) in front with Entra ID as the identity provider. The Bicep does not enable this by default because auth config depends on your tenant.
- **Watchtower -> Azure**: user-assigned managed identity. `DefaultAzureCredential` resolves to the UAMI at runtime via `AZURE_CLIENT_ID` env var, which Bicep sets automatically.
- **Watchtower -> Postgres**: username + password from Bicep, stored in App Service settings. For hardening, switch to Entra auth via `azure_ai` extension.
- **APIM -> Foundry**: system-assigned managed identity on the APIM service, granted `Cognitive Services User` on the Foundry account by Watchtower at intake time.
- **Client apps -> APIM**: subscription key from Key Vault, retrieved via the client app's own managed identity.

## Deploy topology

- Everything lives in one resource group (dev). For prod, split: shared APIM/Foundry/KV in a "platform" RG, Watchtower app in an "ops" RG. The Bicep supports this; you just deploy at the ops RG and pass in the platform resource names.
- No VNet integration by default. Add it if your APIM or Foundry are on private endpoints. Watchtower needs outbound to ARM, Foundry data plane (for RAI), Log Analytics query endpoint, and Retail Prices API (`prices.azure.com`).
